# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SUB/WAVE is a personal internet radio station: one Icecast stream, all listeners hear the same broadcast, AI DJ picks tracks and reads scripts between them. See `README.md` for the architecture diagram and rationale.

## Common commands

Three operator entry points, all driving the same compose files + `state/` layout: the **standalone `subwave` CLI** (single binary, no clone — default for new installs), raw `docker compose` (no-CLI alternative), and `npm start` (contributor convenience inside a clone).

```bash
# --- dev (Mac smoke test, requires git clone) ---
docker compose -f docker-compose.dev.yml up -d     # Broadcast (icecast2+liquidsoap) + Controller (tsx watch)
cd web && npm install && npm run dev               # web UI on :7700, separate process

docker compose logs -f controller        # prod default
curl http://localhost:7700/api/health    # liveness via Caddy edge (prod)
```

The CLI resolves its install location via `SUBWAVE_HOME` (priority: `--home` → `SUBWAVE_HOME` env → `~/.config/subwave/config.json` → cwd if it has a `docker-compose.yml` → `~/subwave` if it exists → error). The cwd fallback is what makes `cd subwave-repo && npm start` work with zero config.

There is no `/skip` endpoint — track-end is the only natural transition. Liquidsoap controls pacing.

**Compose files live at the repo root**, not under `docker/`. One root `.env` is the entire boot config surface — everything else lives in `state/settings.json`, managed by the wizard + admin UI.

**Dev hot-reloads; prod needs a rebuild.** In dev compose, `controller/src/`, `controller/scripts/`, and `radio.liq` are bind-mounted and the controller runs `tsx watch`, so edits restart in-place. In **prod** images `COPY` source at build time, so `restart` reruns the *same baked-in code* — changes need `up -d --build`.

```bash
docker compose -f docker-compose.dev.yml restart controller  # rarely needed — tsx watch handles src/** edits
docker compose -f docker-compose.dev.yml restart broadcast   # after radio.liq edits in DEV (bind-mounted)
docker compose up -d --build controller     # after controller/src/** in PROD
docker compose up -d --build broadcast      # after radio.liq / icecast.xml.template / Dockerfile.broadcast in PROD
```

`web` runs as a Next.js dev server (`npm run dev`) and hot-reloads in dev; prod builds the web image and needs a rebuild like the others.

**Lint is the merge gate; tests are not.** `controller/` and `web/` each expose `npm run lint` (`eslint . && tsc --noEmit`), and `mcp-subwave/` exposes `npm run lint` (`tsc --noEmit`); CI runs all three on every PR (`.github/workflows/lint.yml`, plus a theme-token mirror drift check on `controller`) and those jobs are what block a merge.

`controller/` also has a test suite — `npm test` (`scripts/run-tests.ts`) auto-discovers every `scripts/*.test.ts` and hands the list to **Node's built-in runner** (`node --import tsx --test`), which runs each file as its own subprocess, so a test that fails by `process.exit(1)` and one that fails by a thrown `assert` are caught the same way. **Dropping a `*.test.ts` file into `controller/scripts/` is the whole registration step** — no package.json edit. `npm test -- <substring>` filters to matching files. **Two file shapes coexist deliberately**: the original plain-script shape reports as ONE pass/fail keyed on its exit code (byte-for-byte the old contract, which is why no existing file had to change), while a file using `node:test`'s `test()` reports per assertion. Prefer `node:test` for anything new. Concurrency is pinned to `--test-concurrency=1` — files here reach for shared ground (a temp state dir, the library DB, env vars) and the sequential run is what they were all written against. Note `observatory-scale.test.ts` builds a 200k-track SQLite DB under `os.tmpdir()`, which is a 12 GB tmpfs on a default Arch box; run the suite with `TMPDIR` pointed at real disk if it fails with `SQLITE_IOERR_WRITE`. `web/` and `mcp-subwave/` have no tests. Since CI doesn't run any of this, run `npm test` yourself before pushing controller changes.

## Architecture

Four cooperating processes with **file-based IPC** through a shared `state/` dir (mounted at `/var/sub-wave` in containers). This is the load-bearing fact about how the system works — there is no socket or RPC channel between controller and Liquidsoap.

- **Controller → Liquidsoap**:
  - `next.txt` — controller writes one annotated track URI; Liquidsoap polls every 1.0s, drains, and `request.queue.push`es it.
  - `say.txt` — WAV path; polled every 0.5s, fed through `voice_queue`, **heavy-ducked** (`smooth_add p=0.22`). Station IDs, hourly time, weather, request intros.
  - `intro.txt` — between-track auto-DJ links; polled every 0.5s, fed through `intro_queue`, **light-ducked** (`smooth_add p=0.30`) so the song that just started stays audible under the voice.
  - `auto.m3u` — fallback playlist the controller rewrites every `AUTO_QUEUE_REFRESH_MINUTES` (default 60) for the current mood; Liquidsoap reloads on file change (`reload_mode="watch"`).
  - `liquidsoap_*.txt` (jingle_ratio, crossfade, opus_enabled, opus_bitrate, flac_enabled, aac_enabled, aac_bitrate, …) — tiny files written by `settings.update()`, read once at `radio.liq` startup. Changes need a Liquidsoap restart (controller triggers via `/restart-mixer` → telnet).
- **Liquidsoap → Controller / UI**:
  - `now-playing.json` — written from `music_meta.on_metadata(on_meta)`. The hook must stay on `music_meta`, the **pre-cross** handle captured before `music` is wrapped in `cross(...)`. Hooking the post-cross source fires twice per transition (because `dj_transition` passes `initial_metadata=` into both `fade.in` and `fade.out`), freezing the UI one song behind. `on_metadata` is used instead of `on_track` because `on_track` gets swallowed by source switches (request queue → auto playlist).
  - `jingle-playing.json` — `{filename, startedAt}` written when a jingle starts feeding the jingle rotate (issue #997). Jingles play outside the controller's voice serialiser (and `music_meta` is captured above the rotate, so the incoming track's metadata fires while the stinger is still in the cross buffer); `airVoice` (`broadcast/queue.ts`) reads this and holds every spoken segment until the stinger's window (start + clip length + crossfade) has passed. `jingleRatio: 0` disables jingles entirely (radio.liq skips the rotate; needs mixer restart like every ratio change).
  - `bed-playing.json` — `{filename, startedAt}` written when a track annotated `subwave_kind="bed"` starts (beds — an instrumental the DJ talks over BETWEEN songs, so a long link isn't talked over the song it's introducing). A bed is pushed into `dj_queue` like any other request but is NOT a song: `on_meta` branches on the annotation BEFORE its `title != ""` gate, so a bed never reaches `now-playing.json` and never pushes an ICY title. That silence is also why the marker exists — the controller learns "the bed is on air, air the link now" only from this file (`queue.onBedStarted`, read on the same 1.5s now-playing tick). Same shape and rationale as `jingle-playing.json`.
- **Controller → Web UI**: HTTP. `useStationFeed` (`web/hooks/useStationFeed.js`) polls `/now-playing` + `/state` every 5s.
- **Controller state**: `session.json` — the live DJ session (chat-history JSON, see `broadcast/session.js`); archived to `state/sessions/<id>.json` on roll. Controller-internal, not read by Liquidsoap.
- **Browsers → Icecast**: direct `<audio>` on `…/stream.opus` (Blink) or `…/stream.mp3` (everything else). `usePlayer` (`web/hooks/usePlayer.ts`) probes `canPlayType('audio/ogg; codecs=opus')` once and upgrades to Opus only on a definitive `'probably'` **and** non-iOS, non-Firefox (both choke on Icecast's chained-Ogg page boundary at a crossfade — issues #168/#215). Opus is **off by default** (see Liquidsoap step 9), so a **fourth** gate decides whether the probe runs at all: the station's own `stream.opusEnabled`, published on `/now-playing` and threaded in from `useStationFeed` — only an explicit `true` upgrades, so an un-polled feed or an older controller that omits the key stays on MP3 rather than pointing Chrome at a 404 (issue #1300). That flag is the SETTING, not a live mount probe (it needs a mixer restart), so `onError` still pins MP3 permanently for the session on a genuine Opus failure. The upgrade never retargets a playing element — it lands on the next `tune()`/`reconnect()`, so tapping play before the first poll rides MP3 for that session. MP3 is the universal floor (Sonos, hardware radios, car receivers, pre-iOS-17 Safari). `useMediaSession` wires lock-screen / headphone / CarPlay controls, artwork from the controller's `/cover/:id` proxy.

### Docker layout

Three compose files at the repo root, three deployment shapes:

- **`docker-compose.yml`** — prod single-host with bundled Caddy. **The default.** `broadcast` (icecast2+liquidsoap), `controller`, `web`, `caddy`. **Only Caddy binds a host port** (`${CADDY_PORT:-7700}:80`); the rest are internal. State path `${STATE_DIR:-./state}`. Cloudflare terminates TLS (`auto_https off`). `controller` is forced `NODE_ENV=production` → admin gate mandatory. Configs baked into images, not bind-mounted.
- **`docker-compose.byo.yml`** — prod for hosts with their own Traefik/nginx/Caddy. Same as default minus bundled Caddy; `web`/`controller`/`broadcast` bind host ports (`${WEB_PORT:-7700}`, `${CONTROLLER_PORT:-7701}`, `${ICECAST_PORT:-7702}`). The web image is baked for same-origin `/api` + `/stream.mp3`, so the operator's proxy must replicate `docker/Caddyfile`'s route table on one hostname; split hostnames need a web rebuild with `NEXT_PUBLIC_*`.
- **`docker-compose.dev.yml`** — Mac local smoke-test. Broadcast + Controller only (web runs separately via `npm run dev`). State `./state`. Bind-mounts `radio.liq`, `sounds/`, `controller/src` so dev edits need no rebuild.

**Optional `tts-heavy` profile** in all three composes — a `tts-heavy` sidecar (`profiles: ["tts-heavy"]`, does NOT start unless `docker compose --profile tts-heavy up -d`) hosting Chatterbox + PocketTTS over HTTP on the shared `/var/sub-wave` volume. Off by default keeps the install lean. It is **TTS-only** — acoustic analysis was moved out into the standalone `analyzer` service (see below).

**Default-on `analyzer` service** — the acoustic-analysis sidecar (`subwave-analyzer` image, `docker/Dockerfile.analyzer` + `docker/analyzer/server.py`). **Starts by default** in all three composes (no profile gate — like controller/web); only `tts-heavy` (voices) stays opt-in. It's the librosa (+ optional CLAP + Demucs) analyzer **split out of tts-heavy**: bpm/key/intro/loudness always, plus **outro analysis** on every tier (last ~20s of each *complete* file → `tracks.outro_json`: fade-vs-cold ending, tail LUFS/tempo/bars; a byte-capped download skips it — the completeness flag rides the analyze request). The outro is what makes transitions ending-aware: `queue.applyMixTransition` stamps each DJ-mode track's OWN exit canvas from its measured ending via `mix.endingCrossSecondsFor` (a fade rides out 8–12s, a cold end cuts ~4s; washout/loop overwrite it) — the per-track answer to #749, which blocks the pair-sized `crossSecondsFor` from ever being applied — and a measured fade vetoes the `chop` effect (`effectAllowedFor`). **Vocal-aware transitions** (heavy tier, vocal detection on): the outro window gets its own Demucs pass → `outro.vocalRanges` (absolute ms, `[]` = instrumental tail; backfill widened via the `tail_vocal` capability flag so stale analyzer images never churn; lyric-decided tracks skip the tail Demucs pass like the head one — their tail ranges are clipped from the synced-lyric timing instead, `lyric-vocal.clipRangesToTail`) — a sung fade pulls its exit canvas to the 8s floor (`Analysis.vocalTail`), a sung ending vetoes `chop`, and a *measured* first-vocal entry under 2.5s drops the DJ link outright (`enforceIntroBudget` — see `docs/stem-transitions-research.md`); "sounds-like" embeddings (multi-window CLAP — start/mid/late windows averaged, so quiet intros don't misrepresent the track), vocal ranges, and the CLAP **text tower** (`POST /embed-text`, capability-flagged in `/health`) are the heavy tier. Text and audio vectors share one 512-d space, which powers the picker's `searchBySound` tool (describe a sound in words → audio KNN) and zero-shot audio moods (`music/audio-moods.ts`: mood-vocab prompts scored against stored audio vectors at the end of every analysis pass → `tracks.audio_moods`, blended into `songsByMood`/`trackMoods`; vocab/prompt changes re-score via `mood_vocab_hash`). **Two published flavours**: `subwave-analyzer` — **LEAN, multi-arch** (~1.1GB — librosa + ffmpeg, no torch — the default everyone pulls), `WITH_CLAP=0 WITH_DEMUCS=0`; and `subwave-analyzer-heavy` — CLAP+Demucs baked (~1.9GB, amd64-only), `WITH_CLAP=1 WITH_DEMUCS=1`. **Opt-in switch is `ANALYZER_HEAVY=1` in `.env`** — the compose `analyzer` service resolves `image: …/subwave-analyzer${ANALYZER_HEAVY:+-heavy}:…` and its `build.args` key off the same var (so pull and local build agree). No `platform` pin (lean is native arm64; heavy on arm64 needs `DOCKER_DEFAULT_PLATFORM=linux/amd64`). Uses the **same `analyze_worker.py`** as the offline CLI (single source of truth). The controller resolves its analysis backend from `config.analyzer.urls` — **`ANALYZE_URL`** (`music/analyzer.ts` probes `/health`), then a local venv (`ANALYZE_PYTHON`). tts-heavy is TTS-only now and is **not** an analysis backend (no `TTS_HEAVY_URL` fallback). **AIO (`Dockerfile.aio`) bundles the analyzer in-process** (local venv, `ANALYZE_PYTHON` + `HF_HOME` under the state dir) rather than a service; `subwave-aio` is lean, `subwave-aio-heavy` bakes CLAP+Demucs. The analyze worker lives in the analyzer image(s) and the AIO.

**Image-first pulls, source-build fallback.** Every service references `ghcr.io/perminder-klair/subwave-{caddy,broadcast,controller,web,tts-heavy,analyzer}:${SUBWAVE_VERSION:-latest}` alongside a `build:` block. `up -d` pulls; `build && up -d` rebuilds. Publishing via `.github/workflows/publish-images.yml` on tag pushes (`v*`).

**Auto-generated Icecast secrets.** The broadcast entrypoint (`docker/broadcast-entrypoint.sh`) resolves `ICECAST_*_PASSWORD`: env override → persisted `state/icecast-secrets.env` → freshly generated hex, then writes back and exports into liquidsoap's env. icecast + liquidsoap share one container, so there's no cross-container handshake. To rotate: delete `state/icecast-secrets.env` and restart `broadcast`.

**Private station mode (#478).** `settings.privacy` holds two independent locks over ONE shared `password`: `privatePlayer` (the web player pages ask for it before rendering — shell-level in `PlayerShell`, rides `/state`, applies live) and `listenerAuth` (Icecast listener auth on every stream mount). Either lock being on requires a password — `settings.update()` throws otherwise, because a lock with no password behind it either fails every listener closed or renders a prompt nobody can satisfy. Listener auth uses Icecast **URL auth**, not htpasswd: `settings.update()` writes `state/icecast_listener_auth.txt`, and the broadcast entrypoint (+ AIO supervisor's `render_icecast()`, re-run on every pair relaunch) renders per-mount `<authentication type="url">` blocks pointing at `POST /listener-auth`. External clients send basic auth (`user:pass@`), the web player rides `?auth=` on the mount query (Icecast forwards the query string in the auth callback; browsers can't basic-auth an `<audio>` element). **Two endpoints, opposite failure modes — do not merge them**: `POST /listener-auth` (Icecast) fails OPEN when `listenerAuth` is off, covering the window where icecast.xml still carries the auth blocks but the setting is already off; `POST /station-auth` (the web gate, rate-limited) fails CLOSED, because `privatePlayer` can be on while `listenerAuth` is off and reusing the Icecast decision there would accept any password. Both live in `util/listener-auth.ts`, pinned by `scripts/listener-auth.test.ts`. Toggling `listenerAuth` needs a mixer restart (rides `requiresRestart`); password changes apply live. `/listen.pls`/`/listen.m3u` 403 while auth is on. Settings UI lives in the **Station** section. See `docs/private-station.md`.

**Public persona disclosure.** `settings.privacy.publishPersonaSouls` (default `false`) sits in the same block but is **a disclosure toggle, not a lock** — it takes no part in the password invariant above, needs no restart, and applies live. It governs the ROSTER-WIDE public reads: `GET /schedule`'s persona index and `GET /personas`. Those always publish `id`/`name`/`tagline`/`avatar` (and each show's `guestPersonaIds`, resolved against the live roster so a deleted guest vanishes); a persona's `soul` rides only when the toggle is on, because a soul is the persona's **system prompt**, not a written bio, and these reads hand over every persona at once. When off the key is **absent, not empty**, so a client can tell "not published" from "published but blank" (`/personas` also reports `soulsPublished`). `GET /dj` is deliberately **out of scope** — it has always published the ON-AIR persona's soul, one at a time, and gating it would break existing public clients. The shape + rule live only in `util/public-persona.ts` (never inline in the route), pinned by `scripts/public-persona.test.ts`. Never widen the shape to TTS config, skills, or the behaviour dials.

**Single config surface.** Three required root `.env` vars boot the stack: `ADMIN_USER`, `ADMIN_PASS`, `SITE_URL`. Everything else is collected by two converging wizards — `npm run setup` (terminal, `cli/src/commands/setup.ts`) and `/onboarding` (browser, `web/components/onboarding/*` → `controller/src/routes/onboarding.ts`). Both persist to the same layer: Navidrome creds + setup timestamp → `state/setup-config.json`; cloud LLM/TTS keys → `state/secrets.env` (mode 0600, sourced on boot via `setup/secrets.ts`); everything else → `settings.update()` → `state/settings.json`. **Env always wins**; wizards only fill gaps. `setup/firstRun.ts` decides `needsSetup` (no Navidrome creds from env or config); `/state` exposes it so the player + AdminShell redirect a fresh operator to `/onboarding`.

The shared `/var/sub-wave` mount in **both** Broadcast and Controller is what makes the file-based IPC work — they must always map to the same host path.

### Jingles

`state/jingles.m3u` is empty by default. Run `scripts/generate-jingles.sh` after the stack is up — it `exec`s into the controller, pipes text through the configured TTS engine, writes WAVs into `${STATE_DIR}/jingles/`, rewrites the M3U. The jingles `playlist(...)` uses `reload_mode="watch"`, so new renders need no restart.

## Working on this codebase

- **Queue/playback path**: `queue.drainToLiquidsoap()` is the single writer of `next.txt` (+ request-intro `say.txt`); `queue.announce()` is the single writer of scheduled `say.txt`/`intro.txt`. Request-intro WAVs are written ~250ms before the track URI so the 0.5s voice poll picks them up first. Poll intervals (1.0s queue, 0.5s voice) are the upper bound on perceived latency. **Pair-aware drains** (`transitions.pairDrain`, default on, **DJ-mode personas only** — `queue.pairDrainActive()`, `broadcast/drain-policy.ts`): picks are HELD unsent until their successor is queued behind them (the deadline routine in the watcher tick picks it ~120s before the on-air track's effective end, `min(duration, cue_out)`, with a failure-retry cooldown of `DEADLINE_PICK_COOLDOWN_SEC`; hard fallback ~45s drains with intrinsic stamps), which is what lets `applyPairStamps` finally apply the pair-sized `crossSecondsFor` (#749) and lets stem blends insert. A successor of ANY kind releases the hold (a request IS the successor arriving — FIFO is never inverted); unknown clock (boot/recover/untracked auto) or a non-DJ persona drains eagerly, byte-for-byte the old behaviour. **Operator skips commit first (#1300 bug 6)**: because the hold makes an empty `dj_queue` the NORMAL mid-track state, `POST /dj/skip` runs `queue.commitBeforeSkip()` — force-drain plus a bounded wait for the `dj_queue_status` telnet probe to report a RESOLVED request (a sent-but-still-fetching request loses the fallback race just the same) — before the telnet `skip`; on timeout the skip proceeds anyway and the response/booth log say the pick wasn't confirmed, so `auto.m3u` filling the slot is reported, never silent. Policy in `broadcast/skip-policy.ts`, pinned by `scripts/skip-policy.test.ts`; an empty queue keeps the bare-skip path byte-for-byte. **Stem blends** (`transitions.stemBlends`, opt-in; `broadcast/stem-blend.ts` + worker `render_transition`): at a pair drain, a cache-hit-only render mixes the outgoing tail stems × incoming head stems (`state/stems/`, written during analysis when `audio.stemCache` is on) into a clip that airs between them — outgoing cues out at the blend start, the clip carries the INCOMING track's identity (now-playing flips at blend start; `lastSeenKey` dedups the real fire; `subwave_clip="1"` keeps telnet rid helpers honest), incoming cues in past its pre-mixed head. Any miss → plain pair-aware crossfade. **A clip carries no `liq_amplify`** (`subsonic.getClipUri`), so its LEVEL is whatever the render baked in: both sides are gained by `music/loudness.ts` `resolveGainDb` — the same figure the drain stamps on a real track — never by re-deriving from the analyzer's leading-window LUFS, which ignores ReplayGain tags (the default source), the boost cap and the peak headroom cap and is what made rendered seams sit at a different level than the tracks around them (#1240). The render's peak guard ducks the BORROWED loop to fit the ceiling rather than scaling the whole clip, because scaling the clip is scaling the incoming track's own content back out of match. Pinned by `scripts/stem-blend-level.test.ts`. Clips sweep after 1h (clips still queued for an unaired seam are exempt — `queue.pendingClipPaths()`); the stem cache is byte-budget LRU (`audio.stemCacheGb`, 1–1000 GB, edited in Settings → Transitions), and tail stems carry a `tail-meta.json` alignment sidecar (exact decoded tail offset — the render treats stems without it as a miss). **The stem cache backfills** like the CLAP/vocal scopes: `tracks.stems_at` (schema v17) stamps every stem ATTEMPT, `db.needsStemsIds()` is the fourth widening in `runAnalysisPass`, so turning the cache on for an already-analysed library fills in over successive resumable passes instead of needing a `--re-analyze` (which wipes every vector and can't resume). The stamp records the attempt, **not disk presence** — the LRU sweep evicts dirs by design, so a presence-based scope would re-separate every evicted track forever on any library bigger than the budget; a miss at seam time just falls back to a plain crossfade. **The budget gates every stem write, not just the widening (#1257)**: `runAnalysisPass` takes ONE `headroomTracks()` figure per pass and spends it per NET-NEW dir via the pure `stemCache.stemWriteDecision` (a rewrite of an existing dir is free) — ride-along stems used to bypass the cap entirely, which is how a vocal backfill grew a 500 GB budget to 674 GB. Headroom is sized off the cache's own measured average once it holds ≥50 dirs (`estimateTrackBytes`; the fixed 25 MB guess ran ~2x pessimistic in the field), and `sweep()` reports `failedDirs`/`overBudgetBytes` so a sweep that can't evict (permissions on a relocated stems mount) is loud in the booth log, the analyze event log and the doctor instead of returning `{removed: 0}` and reading as "nothing to do". The admin queue badges seams arriving via a rendered blend (`stemSeam` on `queue.snapshot()` items — stamped at pair drain, cleared on cancel, definitive rather than predictive). Pinned by `scripts/stem-backfill.test.ts` + `scripts/stem-cache-sweep.test.ts`.
- **`radio.liq` `on_metadata`**: keep it on `music_meta`, the pre-cross handle (post-cross fires twice; `on_track` gets swallowed by source switches). See Architecture.
- **`radio.liq` atomic marker writes (#1240)**: every `file.write(atomic=true)` — `now-playing.json`, `jingle-playing.json`, `bed-playing.json` — MUST carry a `temp_dir=` on the state fs (`ensure_tmp_dir` at the top of the file, one dir per writer). Without it Liquidsoap picks a temp dir under `$TMPDIR`, which on Docker is the container overlay while the state dir is a bind mount: the rename is cross-device, the stdlib logs `Atomic rename failed` and silently degrades to a NON-atomic copy — i.e. the half-written-JSON race `atomic=true` exists to prevent was never actually prevented on any Docker install. One temp dir **per writer**, because the stdlib always names the temp file `atomic.write` inside the dir it is given and the jingle write is `synchronous=false`. `ensure_tmp_dir` probe-writes and returns `null` on failure (`file.mkdir` does NOT raise), so an unwritable state mount degrades to the old behaviour instead of raising inside `on_metadata`.
- **`radio.liq` emergency dead-air fallback position (#1300 bug 7)**: `fallback(id="music_safety", track_sensitive=false, [music, emergency])` MUST stay **above every `add` in the music path** — both the `smooth_add` ducking layers AND the studio-bed mix. It binds to `music`, immediately BEFORE the `bed_enabled` if/else. Anything below an `add` can never fire, because `add` is ready if ANY input is: the stdlib builds smooth_add as `add(normalize=false, [normal, fallback(track_sensitive=false, [special, blank()])])`, that inner fallback falls through to `blank()` so it is ALWAYS ready, and the bed leg is `mksafe(single(bed))` — `mksafe` makes it INFALLIBLE. Either way the bus reports ready with the music chain starved and a fallback under it selects index 0 forever. The guard lived at the BOTTOM of the chain for its whole life and was dead code the entire time; nobody noticed because the failure it guards against also needs the jingle rotate silenced, and the rotate had been masking every starve (that's bug 7 itself). Gating jingles off without moving this turns "stingers forever" into digital silence forever — measured -91.0 dB at the output, versus -3.0 dB with the fallback in its correct position. The bed trap is the same bug re-armed by a **documented** one-line source edit (`bed_enabled = true`, "flip back to `true` to restore it"): measured on the full chain with the bed on, the guard bound to `music_bus` never selected `emergency` at all and the output was the bed alone at -57.1 dB, versus -9.0 dB (the loop, at its own level) with the guard bound to `music`. **Do not leave a second one at the bottom** "for safety": a fallback that looks like a dead-air guard but structurally cannot fire is what caused this. Position also matters upward — it stays BELOW `music_meta` and the jingle rotate so now-playing metadata and jingle counting are untouched. A harness that tests this guard MUST build the duck layers (and, for the bed claim, the bed `add`); one that runs `output.dummy` on the bare rotate proves nothing (that is exactly how the false claim got shipped).
- **`radio.liq` emergency fade-in — not a debounce (#1300 bug 7)**: the guard's emergency branch ramps up over `EMERGENCY_FADE_SEC` (1.0s). `track_sensitive=false` makes it switch the instant `music` reports not-ready, and now that it can actually fire it also fires on brief real gaps — cold boot before `auto.m3u` resolves, and track seams where `dj_queue` and `auto_playlist` are momentarily both unready (auto entries are whole-file `subhttp:` downloads, so a slow Navidrome widens the window). **Never "fix" that by delaying the switch**: a dead-air guard that waits before firing is a guard that doesn't fire, which is the exact bug class above. Fire immediately, ramp the LEVEL — a sub-second stab is inaudible, a real starve is at full level in ~1s, timing untouched. It takes **two** fades and both must stay: `switch` applies no transition to its FIRST selection (measured — `Switch to emergency.` at boot vs `…with transition.` after), and boot IS that first selection, so `emergency` carries its own one-shot `fade.in` (default `track_sensitive=false` memoises the ramp to the source's first frame ever — right for boot, useless later, since a looping single never reaches a fresh track boundary); the `transitions=` entry then ramps every later switch. The music branch keeps the stdlib identity transition — coming BACK must be instant, or a recovered station fades up over its own first second of music. `fade.in` returns extra methods, so both sites cast `(… : source)` to unify with the plain `music` child. Measured (100ms RMS): boot -38.5 → -9.0 dB over 1.0s, mid-run -32.6 → -9.0 dB over 1.0s, recovery a single-window step with no ramp, unchanged after 43 switches in one process.
- **Crossfade**: keep fade duration equal to the cross buffer (`d = crossfade_duration()`, `fade.out(d)` / `fade.in(d)`). Shorter fades inside a fixed buffer let the outgoing track play full while the incoming ramps, summing to +6 dB (audible doubling). Vary the buffer length instead.
- **Spoken clocks on pick-attached links (#864 → #1282 → #1314)**: a link is written when the pick is MADE but airs when the pick STARTS, so any time it speaks is a **forecast** — `linkAirDate(showAt)`, i.e. now plus whatever is left of the on-air track. The forecast holds only if the pick reaches Liquidsoap before that track ends; when the round outruns it, `dj_queue` is empty at the seam, `auto.m3u` fills the slot and the pick airs at the END of that filler, with the link still naming the moment the filler STARTED (#1314's ~4-minute undershoot). #1282's removal of a fixed +120s show-attribution overshoot is what exposed it — the two errors had been cancelling. **Two guards, both in `broadcast/queue/pure.ts`, and they must stay paired**: `linkClockAt(showAt, now)` refuses to hand the generator a clock at all below `LINK_CLOCK_MIN_RUNWAY_SEC` (= `DRAIN_DEADLINE_SEC` — `maybeDeadlinePick`'s empty-queue backstop always fires inside that window on any station, whatever its track lengths; measured over 788 rounds, 27.7% ran past 45s of runway but only 0.3% past 120s; accepted flip side: a sub-2-minute-track library never clears the floor even at track start, so its links never speak the clock at all), and `linkClockDrifted` drops the line at `airIntro` when the real seam lands more than `LINK_CLOCK_DRIFT_TOLERANCE_SEC` (90s) from the stamped `item.linkClockAt`. Runway is read from the LIVE clock at generation, never from the `leadSec` `showAt` was built with — on the pool path the pick call has already spent part of it. The stamp records the clock being **offered**, not used: unlike `shouldDropStaleLink`'s `mentionsTrack`, a clock has no reliable string handle ("18:38" / "twenty to seven" / "eighteen thirty-eight"), so don't narrow it with a regex. Note that even a perfect forecast is heard `stream.bufferSeconds` late — see the next bullet.
- **Listener buffer / live-edge offset (#1114)**: Icecast bursts `settings.stream.bufferSeconds` (default 22s) of already-broadcast audio on connect, so **every listener sits that far behind the live edge for their whole connection**. Two consequences that must stay in sync. (1) `<burst-size>` is a BYTE count, so it's computed **per mount** — `bufferSeconds x that mount's bitrate x 125`, rendered as one `<mount>` block per stream mount by `docker/broadcast-entrypoint.sh` (and the AIO's `render_icecast()`, kept in lockstep), reading `liquidsoap_stream_buffer_seconds.txt` + the per-encoder bitrate files from the state dir; FLAC is VBR so its depth uses a ~900kbps estimate. Never collapse this back to one global figure: the same 528 KB that is 22s of 192k MP3 is ~43s of 96k Opus and ~6s of FLAC (the post-#1114 "Now Spinning runs behind" report). Each mount's `<queue-size>` is 4x its burst (floored at 2 MB) and must stay comfortably above it or clients get evicted the moment they fall behind their own primed buffer. (2) Every timestamp the controller publishes is stamped at the **live edge** (`radio.liq`'s pre-cross `on_metadata`), so listener-facing players shift into listener-time — `useStationFeed` holds the track switch until the audio is actually audible and `trackStartedAt` carries the offset (it can briefly sit in the future; `useElapsed` clamps at 0). The offset the web player applies is the advertised `stream.bufferSeconds` from `/now-playing`, full stop. It used to prefer a per-tab **measurement** (`usePlayer.getListenerLagMs`, `buffered.end − currentTime`) because a byte-sized burst meant a different depth per mount; (1) above fixed that at the source, and the measurement was never the offset anyway. **`buffered.end − currentTime` does NOT measure the listener's distance from the live edge** — it reports only the window the browser has DEMUXED, while Chrome holds the connect burst in an internal cache `buffered` never exposes. Measured directly (tone marker vs `now-playing.json`'s live-edge stamp): true offset **22.5s**, `buffered.end − currentTime` **2.25s**, advertised **22s** — so preferring the measurement flipped every title ~20s early. Don't reintroduce it, and don't use `buffered` to judge cushion health. Operator surfaces (admin dash, MCP) intentionally keep live edge. Changing the depth needs a broadcast **container** bounce, not just a mixer restart — though the telnet `restart` achieves it anyway, since icecast and liquidsoap share a container the entrypoint `wait -n`s on.
- **Real listener IPs / trusted proxies**: Icecast's only peer is the edge, so admin → Listeners shows the proxy's container IP unless `<x-forwarded-for>` names that proxy. Rendered into the template's `<!--@TRUSTED_PROXIES@-->` marker by `docker/broadcast-entrypoint.sh` and the AIO's `render_icecast()` — the **third** thing those two must keep in lockstep, alongside the per-mount burst/queue and the listener-auth blocks. Two icecast-KH facts pin the design: it matches an **EXACT IP** (a CIDR is accepted and then silently never matches, so no subnet shorthand), and it reads the **left-most** entry of the chain (the real client, even though Caddy appends its own peer). Source order is `ICECAST_TRUSTED_PROXY_IPS` (explicit, wins) → DNS for `ICECAST_TRUSTED_PROXY_HOSTS` (default `caddy`). The DNS path is **deliberately best-effort and misses the first cold boot** — caddy `depends_on` broadcast being healthy, which needs icecast already serving, so the name cannot resolve at render time (measured: ~6s unresolved); every later restart picks it up. A miss degrades to the old behaviour (proxy IP shown), never to a wrong IP, so nothing downstream handles a half-applied state. The AIO trusts loopback outright (Caddy is in-container). Malformed entries are dropped rather than interpolated — invalid XML here would turn a cosmetic setting into a station that won't boot. Counting still must NOT key on IP (`groupConnections`): the header may be untrusted, and one NAT is many listeners.
- **State bootstrap is never fatal (#1300 bug 10)**: `bootstrap_state_dirs` in `docker/broadcast-entrypoint.sh` and the AIO's `supervisor.sh` (same function, same list, same messages — the **fourth** thing those two keep in lockstep) creates the shared state dirs and opens them to 777, because the controller and analyzer write there as other uids. Every step is guarded and warns instead of aborting. The entrypoint runs `set -eu`, so the old bulk `mkdir -p a b c` / `chmod 777 a b c` made **every state path load-bearing**: one on a mount that refuses the change — a read-only bind, an NFS export, the exFAT/NTFS disk people move the stem cache to — exited the entrypoint BEFORE icecast started, and compose reported only `dependency failed to start: container sub-wave-broadcast is unhealthy`, naming neither path nor cause (measured: `exit=1`, `health=unhealthy`, one `chmod:` line). A station that refuses to boot over a permission convenience is strictly worse than one on a degraded mount — icecast still serves and the dead-air guard still airs the emergency loop, but an exited container airs nothing. The warning keys on **writability, not on chmod's exit status**: a mount already world-writable that merely refuses chmod is a WORKING config, and a line printed on every boot of a healthy station is one operators learn to skip. `stems` + `transitions` are in the list because a bind mount at `<state>/stems` is the only way to relocate the stem cache (`stemsRoot()` has no setting behind it) and a fresh one lands root-owned 755, which the analyzer (uid 10001) cannot write — measured `ANALYZER_WRITE_DENIED` before, `_OK` after. Pinned by `scripts/state-bootstrap.test.ts`, which drives BOTH scripts through one table.
- **Listener-count gates (#1256)**: **three** gates fail **OPEN** on an unknown count, and all three read a gated reading, **never the raw `getListenerCount()`** — `listeners.djCallsAllowed()` (all autonomous DJ/LLM work, plus `POST /request`) and the idle-pause monitor (`broadcast/stream-idle.ts`) via `listeners.gatedListenerCount()`, and the analysis quiet gate (`music/analyze-quiet-pure.ts`, whose fail-open runs the OPPOSITE way — an unknown count lets the DSP pass proceed) via `probeListenerCount()`, which returns the gated count from the tagger child's own module state. A failed Icecast status poll is not an observation: the pure `gatedCount` holds the last count actually read from Icecast until failures reach `STALE_STATUS_LIMIT` (4), the same hysteresis the cached `StreamStatus` has carried since #461. On the raw count a **single** `fetchWithTimeout` abort read as "unknown" and the gates opened at once — and because `stream-idle.ts` deliberately forces its own poll every 5s while paused (~120 per 10-minute pause, not the 15s monitor cadence a short manual probe would sample), a sub-1% poll failure rate released nearly every pause ~28s after it engaged: the power save was inactive ~95% of the time it should have been active, and each release also reopened the LLM token gate. Fail-open itself is unchanged — a *sustained* outage still reads null, still resumes, still keeps the DJ on air. Two things keep the failure RATE down rather than absorbing it: the poll is `singleFlight()`-coalesced so the 5s, 15s and on-demand cadences can't race each other into an `AbortError`, and `STATUS_TIMEOUT_MS` is 3000 (not the original 1500) — widening `STALE_STATUS_LIMIT` instead would have slowed #461's offline detection, which is a different contract sharing the same constant. `FIRST_POLL_WAIT_MS` is derived from `STATUS_TIMEOUT_MS`, not written flat, so raising the deadline can't silently un-do the boot await. `presentListeners()` deliberately stays on the RAW count: it fails **CLOSED**, where a blip costs at most one skipped scrobble, which is the safe direction — don't unify it onto the gated reading. `startListenerMonitor()` is awaited before `queue.startWatcher()` so "never polled" can't buy a free agent pick on every restart. Pinned by `scripts/listeners-status.test.ts` and `scripts/stream-idle.test.ts`, which replays 120-poll pause AND live windows through both helpers.

- **The `/settings` patch registry** (#1348, split out of #1337): `POST /settings` is the one body that is a **partial patch over 42 top-level keys**, not an object, so there is no single schema to hand `validateBody` — one over the whole settings object would `z.object`-strip whatever a form learns to send next. `settings/patch-registry.ts` is the frame instead: `SETTINGS_PATCH_KEYS` (every key `update()` acts on, **in branch order**), `SETTINGS_PATCH_SCHEMAS` (the converted subset), `parseSettingsPatchKey()` (strict, used INSIDE `update()`, throws a plain `Error`) and `validateSettingsPatch()` (route posture, via `middleware/validate.ts`'s `validateSettingsBody()`, returns `{error, fieldErrors}`) — the same schema on both, which is what finally gives the dozen panels posting here the `fieldErrors` channel #1323 built. Converting a key is ONE edit: add its schema to the registry and switch its branch to `parseSettingsPatchKey`; the other 39 keep their hand-rolled branches, so the frame lands without a flag day. Branch order is load-bearing twice — `update()` applies moods before the orphan guard and personas before shows before schedule, and the route iterating the same order means it names the SAME first failure rather than a second opinion that depends on JSON key order. **Unknown top-level keys are rejected at the ROUTE and never inside `update()`**: `routes/backup.ts` hands `update()` a whole backup `settings.json`, so a key from a newer version must cost one setting, not the entire restore — the same reason unknown fields INSIDE a block are dropped rather than refused. The flat `error` string is the zod message **verbatim** — the one place that bypasses `firstMessage`, because every message here is custom and already names its full dotted field, so prefixing would read `crossSec: beds.crossSec must be …`; that invariant is enforced structurally (hostile values thrown at every registered schema) rather than trusted. **26 of the 42 keys are converted, at zero behaviour change**, and that fidelity is most of the work: the branches carry accidental leniency the obvious conversion silently removes. **FIVE numeric coercion families** are in play and reusing the wrong one changes behaviour in one direction or the other — `parseInt` (truncates a float, reads leading digits from junk), `parseFloat`, `Number` (refuses `'10abc'`, but `''`/`null`/`[]` are 0 — the opposite of parseInt on both counts), `Number`+`floor`, and `Number`+`round` where the round runs BEFORE the bounds test, so `likes.maxTracks: 0.6` is accepted as 1 while `0.4` is refused and `25.4` is accepted while `25.5` is refused. Plus **FOUR string families**: `String(x)` with no trim (`search.apiKey` stores `'null'` for null), `String(x).trim()`, `String(x ?? '').trim()` (scrobble — null CLEARS the field), and a `typeof` check that refuses (`search.baseUrl` only, where `scrobble.listenbrainz.baseUrl` with the same message tail coerces instead). **`embedding`**: `providerBaseUrls` merges into the existing map with delete-on-empty, `baseUrl` is a write-through into that map under a provider that may come from `llm`, and a re-derive runs on - **Blocklist rules** (#1300 FR 1, closes #752): the never-play blocklist carries **rule entries** beside the id entries — attribute predicates (`genre`/`tag`/`mood`/`artist`/`album`/`title`/`playlist` + any-of values) with an optional seasonal **allow-window** (inclusive month/day, wraps year-end, station zone) and an optional show scope — same `blocklist.json`, same routes, same Blocked tab. Pure matching lives in `music/blocklist-rules.ts` (pinned by `scripts/blocklist-rules.test.ts`); `blocklist.ts` owns the evaluation context — a ~15s-memoised active-rule set (clock via `zonedParts`, show via `resolveActiveShow`, both resolved once per sweep, NOT per track) and pre-resolved playlist member sets (the one async input, so `matchOf` stays synchronous). **Enforcement is inherited, not added**: rules ride `hitOf()`/`isBlocked()` inside the existing chokepoints (subsonic reject, library sources, `queue.push` gate, request declines, `annotate`) — never add a second rule-filter at a pick path, that's how the two kinds would drift. `hitOf()` answers entries-FIRST (the UI unblocks exactly the entry), and `BlockRef` is now a `kind: 'entry' | 'rule'` union. Rules are absolute like the id list — no never-starve anywhere, requests included; the row UI deliberately offers **no one-click unblock for a rule ref** (one rule can block hundreds of rows — edits happen on the Blocked tab). `tag` matches EXACT-normalised across every ingested namespace (genres ∪ moods ∪ audioMoods ∪ Last.fm — `show-filter.trackAllTags`); `genre` reuses `genreMatches`' refine direction (blocking "Punk" drops "Punk Rock", not the reverse). Custom file tags (e.g. a country) only work once they land in a field the pipeline ingests — that's an ingestion boundary, not a rules bug. Spec: `docs/superpowers/specs/2026-08-05-exclusion-rules-design.md`.
